# DNDWORLDAPP — Roadmap Redo (2026-09-23)

## 0. Why this document exists

Two research passes fed this: an earlier UI/UX-pattern survey (chronicler deep-dive, three
batches across the rest of `DNDWORLDREF`, plus live web research on Kanka/World
Anvil/LegendKeeper/Foundry VTT — promised as `docs/UX-RESEARCH-2026-09-22.md` but never
actually written; folded in here instead, superseding that promise) and a second pass,
triggered by the owner proposing a much bigger shape for the whole project: not just a
web app, but **a website (host) + a DM desktop companion app + an eventual player app**.
That second pass re-surveyed every remaining folder in `DNDWORLDREF` specifically through
an architecture-fit lens, plus targeted research on Kanka's icon/relation model, graph-view
tech, and multi-app precedent. `docs/obsidian-plugin-inspiration.md` in `DNDWORLDREF`
(written during the first pass) is a third input, covering six named Obsidian plugins plus
a "read the room" adaptive-music idea.

This doc is the synthesis: what the research actually found, what it means for near-term
work (mostly P3, already in flight), and a proposed phase order for the bigger three-app
vision. It does not replace `docs/PLAN.md` — that stays the schema/phase reference for
what's built — this is the decision record for what changes and why.

---

## 1. The vision: three apps, one host

- **The website** — today's DNDWORLDAPP web app, repositioned explicitly as the system's
  data host and aggregator. Owns the database, the REST API, the MCP server. Every client,
  including its own web frontend, is just another API consumer — this is *already* a
  stated project rule (`README.md`, `docs/PLAN.md` §7), not new work, and the research
  confirms it's the single most important thing to keep true as more clients arrive.
- **A DM desktop companion app**, Linux-first — a thick client hitting the website's API.
  Hosts session audio transcription, a soundboard, and other LLM agents working alongside
  the DM. Does not own game-state data; the website remains the source of truth.
- **An eventual player-facing app** — phone and/or another desktop app, lighter,
  player-scoped. Research recommendation (§5 below): build this as a **mode**, not a
  separate binary, at least initially.

## 2. What's already true today (verified, not aspirational)

Confirmed by reading `docs/PLAN.md`, `README.md`, and `docs/openapi.json` directly, not
assumed:

- **Public-API-only rule already holds.** The web client has no private backend routes.
- **OpenAPI is already generated from the Zod schemas** (`npm run openapi` → `docs/openapi.json`).
  This directly satisfies the research's "generate a real OpenAPI spec" recommendation —
  it's done, not a gap. What's *not* yet verified: whether the generated spec is complete
  enough for a code-generator to produce a working non-TS client from cold. Worth a real
  test (point `openapi-generator` or similar at it) before the desktop companion starts.
- **Scoped bearer tokens already exist**, mintable from the sidebar, revocable, pinnable to
  one world (`world:read`/`world:write`/`admin` scopes). This is exactly the auth mechanism
  a desktop companion needs — no new auth system required, just a token-acquisition UX
  (§5).
- **The MCP server is already a thin client of the public API**, not a privileged path.
  This is the working precedent for "how should the desktop companion's own MCP
  integration be built" — same shape, just running on the DM's machine instead of
  alongside the server.
- **Nothing is realtime/push yet.** `docs/HANDOFF.md`'s "Not started" list already says
  so. This is the one real, load-bearing gap for live-session features (transcription
  results, soundboard cues, a player app watching state change) — see §5.

## 3. Content model: tags, relations, graph (P3 — next up)

Tags shipped 2026-09-22 (`#tag` inline syntax, auto-create/reuse, a "Tags" panel, reverse
lookup via the same backlinks mechanism wikilinks use — see `docs/HANDOFF.md`). Relations
and a graph view are the two pieces still missing, and the research gives a concrete shape
for both.

**Relations** — Kanka's actual data model (confirmed via the community Go client's struct
definitions, mirroring the real API contract):

```
relation: { label, owner_node_id, target_node_id, attitude?, two_way: bool, visibility }
```

Directional by default; `two_way` collapses it to one symmetric label ("siblings," "allies").
An asymmetric pair ("mentor of" / "student of") is just two separate rows with
independently-chosen text — no paired-label field needed, which is simpler than it sounds.
Kanka surfaces this as a "Connections" tab per entity: manually-added relations *and*
auto-populated backlinks shown together. **DNDWORLDAPP should do the same** — a `relations`
table analogous to `node_tags`, and a panel on each node that merges typed relations with
the existing wikilink backlinks, the same way the Tags panel already reuses the backlinks
mechanism for reverse tag lookup. `packages/schema/src/index.ts` needs a new
`relationDtoSchema` (`sourceNodeId`/`targetNodeId`/`label`/`twoWay`/`visibility`), modeled
directly on `mapMarkerDtoSchema`'s shape conventions.

Chronicler's own indexer (parse-at-write-time, maintain a computed inverse-edge set,
`models.rs:76-121` per the research) is a good template for how to compute the reverse
side without a live query every render, once relation volume grows.

**Graph view** — the technical shape, from direct research (not vibes):

- **Library: cytoscape.js.** Actively maintained (pushed within the week at research time),
  canvas-based, comfortably handles hundreds of nodes, has both force-directed and
  hierarchical (`dagre`) layouts built in — useful since parent/child-style relations are
  naturally tree-shaped. `react-force-graph` was considered and rejected: 7 months stale,
  218 open issues, single-maintainer — too much bus-factor risk for a load-bearing
  feature. `sigma.js` (WebGL) is the fallback if the graph ever needs to scale past a few
  thousand nodes.
- **One graph, not three modes, with edge type as the visual variable:**
  - Wikilinks → thin, recessive, near-gray edges (expected majority, ambient connective
    tissue).
  - Relations → bold, colored, labeled, directional edges (the intentional, curated data;
    should read as the dominant layer).
  - Tags → **not edges at all.** Node color/badge, or a togglable filter ("show only
    `#npc`-tagged nodes"). A tag with hundreds of members rendered as a hub-and-spoke would
    drown everything else out — this is a well-documented graph-viz failure mode, and both
    Kanka (which scopes its own interactive graph to relations only, never tags) and
    Obsidian (tags are a color-group/filter, not graph nodes, by default) independently
    arrived at the same answer.
  - Ship a **local** view (one node + its direct/expandable neighborhood) and a **global**
    view (everything, filterable), matching Obsidian's own split — this is a scope
    distinction, not a reason to build separate graph *engines*.

## 4. Page-level features: icons, table of contents, index

**Icons.** Kanka's actual answer to "how do you customize an entity's icon" turned out to
*not* be a richer icon library — it's image upload. An entity has two independent image
slots, avatar and a separate header/cover image, both filled by uploading a file, pasting a
URL, or reusing something already in the campaign's shared Gallery — no searchable
named-icon picker, no icon font. So the real gap in `IconPicker.tsx` (currently a 30-item
emoji grid plus free-text emoji) isn't "more emoji options," it's **"let a node's icon be
an uploaded image thumbnail,"** reusing the asset-upload pipeline that already exists for
map images and inline document images. Keep this explicitly separate from any future
cover/header-image feature, matching how Kanka keeps the two apart.

**Table of contents.** Chronicler has exactly the feature being asked for: a per-page ToC
auto-generated from the page's own headings, nested by level, with a show/hide toggle
(`TableOfContents.svelte`). Direct, low-risk precedent — build the same thing here, scanning
the TipTap document for heading nodes and rendering a nested nav in the right panel (or a
collapsible strip at the top of the body).

**Index (list of everything nested under a page, with the current page's own ToC — the two
being distinct, per the owner's own clarification).** This one has **no real precedent** in
either research pass. Chronicler's closest analog is a per-*tag* index (`TagIndexView.svelte`
— pages carrying a tag, not pages nested under a page) and its own file-tree sidebar (which
is always a full listing, but unannotated). Nobody surveyed has a "folder note" /
auto-generated-descendants-with-summary feature. This is genuinely new work for
DNDWORLDAPP, not a port: a view (or a page-body block, `/index`-style) that walks a node's
full descendant subtree and lists it, richer than the current flat "Child pages" grid
(one level only, no annotation). Reasonable v1 scope: recursive listing, each entry showing
icon/title/kind, collapsible by branch — annotation/summary-per-entry can come later.

**Folder/explorer view request.** Re-reading the specific ask (an Obsidian-style file
explorer) against what's already built: the sidebar tree already *is* this — nested,
drag-and-drop reorder/reparent, right-click actions, search. The gap isn't a missing
feature, it's polish: no sort-order options (alphabetical vs. manual), no per-branch
collapse-all/expand-all. Worth a short follow-up pass, not a new subsystem.

## 5. The website/API layer: what needs to change to support thick clients

Research verdict across five self-hosted/multi-client reference repos (Kanka, Worldbinder,
TTRPG-Toolkit, quest-board-dnd, logseq): DNDWORLDAPP's foundation is already closer to
"right" than any of them, but each surfaced one concrete lesson worth acting on:

- **Don't let the web client become privileged, the way Kanka's is.** Kanka's own web
  frontend and its documented OAuth2 API are two *entirely separate* controller trees
  hitting the same models — the frontend doesn't eat its own dogfood, despite the API
  being genuinely good (rich enough that outside developers built unofficial clients
  against it in three languages with zero official GUI client to prove it). DNDWORLDAPP's
  "no private routes" rule already prevents this — the action item is to keep auditing for
  drift as new endpoints (relations, graph data, realtime) get added, not to build
  anything new.
- **Adopt a real policy-service pattern for authorization, not scattered role checks.**
  Worldbinder's `campaign-policy.service.ts` — independently-testable functions like
  `canManageTarget`/`canViewGmContent`/`canRevealContent` — is a better shape than `if
  (role === 'dm')` sprinkled through route handlers. DNDWORLDAPP's `auth/policy.ts`
  already centralizes this reasonably well; worth an explicit check that every new
  endpoint (relations especially, since a relation's visibility needs to consider *both*
  endpoints' visibility) actually goes through it.
- **Never trust a route-level role split without server enforcement.** TTRPG-Toolkit's
  `gm`/`player` route folders turned out to be a pure CSS theme swap with zero backend
  authorization behind them — worse than no split at all, since it looks secure and isn't.
  Explicit warning for the eventual player-app mode-toggle: the mode must be enforced by
  what the API actually returns for that token/session, never by which UI the client
  chooses to render.
- **The real, concrete gap: no realtime/push.** Every live-session feature the desktop
  companion wants (transcription results streaming in, soundboard state, a player app
  watching HP change) needs *some* push mechanism — polling will not feel acceptable for
  this. This is genuinely new API surface, not something already covered by the REST
  design. Recommend scoping this explicitly as its own piece of work before the companion
  app's live-session features start, likely SSE (simpler, matches the typed-event
  streaming pattern found useful in the LLM-agent research, §6) rather than full
  WebSockets, unless bidirectional push turns out to be needed.
- **Self-hosting ergonomics need to stay exercised, not become an afterthought.** Both
  Kanka CE (self-host assets live in a *separate* companion repo) and Worldbinder (its
  `docker-compose.yml` is explicitly Railway-cloud-only, not a real local self-host story)
  show this eroding once a hosted path exists. DNDWORLDAPP has no hosted path and shouldn't
  get one — keep the root `docker-compose.yml`/Dockerfile as the one true self-host story,
  exercised regularly, not left to rot.

## 6. The DM desktop companion app

This is new product surface, not a port of anything — but three separate research batches
converged on a consistent shape. Recommended architecture, by subsystem:

**MCP/agent integration.** Run the companion's LLM tooling as MCP clients holding (at
least) two server connections: DNDWORLDAPP's own MCP server for world/campaign truth
(characters, locations, NPCs, quests — same pattern as mcp-kanka), and, for rules lookups,
**`dnd-oracle` reused wholesale, unmodified** — a complete, model-agnostic MCP server
(SQLite+FTS5 over the SRD) that needs no changes to plug in. Don't build a rules database
from scratch; this one's already solved. Keep the companion's own MCP surface an
**independent process with an explicitly narrowed, written-down scope** — mimir's own MCP
server states outright, in its init instructions, that live-session DM-only controls (fog
of war, player visibility) are deliberately excluded from what its agent tools can touch,
separate from authoring tools. Same discipline applies here: agents get world-authoring and
rules-lookup tools; live-session state mutation (HP, initiative, reveal/hide) stays a
human-driven action in the companion's own UI, not an agent tool, at least for v1.

**Session transcription.** `faster-whisper`, run locally (in-process or a lightweight
sidecar, matching the separation found in the pen-and-paiper reference), "small" model at
int8 quantization, automatic CUDA→CPU fallback. Confirmed realistic for a DM's own Linux
desktop hardware — this isn't a research question anymore, it's an implementation one.
Client-side chunked capture (a few seconds per chunk) with voice-activity-detection
filtering to skip silence, same pattern pen-and-paiper's `Recorder.tsx`/whisper service
uses (the specific code isn't reusable — no auth, proof-of-concept quality — but the
pipeline shape is right).

**Co-DM / narration agent**, if and when built: the single most important idea across all
three LLM-agent-focused repos is **mechanics-in-code, narration-in-LLM** — never trust the
model's arithmetic for dice, HP, conditions, or initiative; those go through
DNDWORLDAPP's own API/MCP tools or trivial local code, while the LLM's job stays narration
and judgment (open-tabletop-gm's own stated design principle, independently converged-on by
ai-dnd-rpg via a separate "Arbiter" LLM call that decides *whether* an action needs a
mechanical check before the narrator responds — a middle ground worth considering for
anything too fuzzy for pure code). Two more specific patterns worth carrying over:
- **"Live State Flags"** — a small, explicitly-durable block of current facts (who's where,
  what's active) that gets *re-read* every turn rather than trusted from the model's own
  running context — a real anti-hallucination mechanism for exactly the failure mode a
  long session produces (context compaction silently losing specific facts).
- **Typed event streaming to the companion's own UI** — ai-dnd-rpg's SSE contract
  (`chunk`/`roll`/`combat`/`gold`/`xp`/`item`/`quest_update`, parsed server-side from
  tagged LLM output and re-emitted as structured events) is a strong, directly reusable
  shape for how the companion should drive its own display — and pairs naturally with the
  realtime/push work already needed for §5.

**Soundboard.** grimoire's data model is small and concrete enough to lift close to
verbatim: one row per named board (`kind`: playlist vs. soundboard), `entries` as
`[{audio_id, loop?}]` (referencing a shared audio library by id, not copying files per
board), grid `layout`. One `<audio>` element per pad so sounds layer instead of
interrupting each other; a looping pad toggles, a one-shot always restarts. Its floating,
resizable, draggable panel UI (position persisted locally) is also a reasonable reference
for the companion's own always-on-top overlay window.

**Second-screen/projection**, if wanted: start with the cheapest option that actually
works — VeilCast-VTT's `window.open()` to a second same-origin window, redrawing into it
with an independently-computed view transform on every state change. No IPC framework
needed for a same-machine second monitor. Only reach for a true native OS sub-window
(mimir's Tauri `WebviewWindow` + `emit()`, or Flutter's `desktop_multi_window`) if the
overlay needs to survive being a genuinely separate process — and if that path is taken,
budget for real Linux fragility: dungeon-master-tool had to vendor-patch
`desktop_multi_window` because destroying a sub-window on Linux segfaults the whole app,
and ships a "hide, never destroy" workaround as the only safe pattern found.

**HUD/overlay window mechanics**, if the companion wants an always-on-top rules-reference
strip (log-of-beholding-desktop's core feature): the useful, portable ideas are the
technique, not the code — pin to the OS's topmost z-band and *re-assert* it on every
show/display-change (Windows quietly demotes topmost windows; Linux compositors have their
own version of this problem), click-through toggling, and debounced multi-monitor
re-anchoring. The actual speech engine and Windows-specific packaging are not portable —
Linux would need its own native ASR binary and a real compatibility pass, not a recompile.

**Hosting pluggable agents/extensions** more generally: grimoire's addon pattern is the
right template — a declarative manifest (allowlisted field mapping, safe transform
vocabulary) for the common case, and a **consent-gated, isolated subprocess** (no shared DB
session, no imports from the host app, timeout-bounded, crash-detected) as the escape
hatch for anything needing real code — explicitly documented as containment for crashes
and bugs, not a security sandbox against a malicious extension. Worth carrying that
distinction into DNDWORLDAPP's own docs verbatim if this gets built.

## 7. The player app (future)

Recommendation, from the multi-app-architecture research: **one app, a GM/player mode
toggle, not two separate binaries** — Foundry VTT's own approach (all role differentiation
enforced server-side via per-document permissions, one client) rather than shipping a
whole second app. Justification: so much of the DM companion (transcription, soundboard,
agent hosting) a player would never touch that a separate lightweight client is the
better initial investment, and dungeon-master-tool's own `WorldRole: dm | player | none`
enum shows this can live as one thick client with server-derived role rather than two
codebases. Revisit this if/when player-specific needs (a phone-native experience,
push notifications, something DM-app bloat would genuinely hurt) make a truly separate app
worth the cost — not before.

## 8. Updated phase ordering

Supersedes `docs/PLAN.md`'s "Next" line and `docs/NEXT-STEPS.md`'s roadmap section (§2)
for ordering; those docs' schema/status detail stays valid.

1. **P3 continued** — relations (§3), then graph view (§3), then icons-as-images (§4),
   then table of contents (§4), then the index view (§4). Roughly in that order: relations
   and graph are the biggest, most load-bearing pieces and were the owner's explicit
   trigger for this whole redo; icons/ToC are small, low-risk, well-precedented; index is
   the one genuinely novel piece, sequenced last so it can build on however the ToC work
   shapes the "walk the document/tree" code.
2. **P4.4 — Fog of war.** Unchanged from the existing roadmap, still next after P3's
   content-model work in the original ordering — revisit priority once P3 above lands.
3. **API/realtime groundwork** (§5) — the one genuinely new prerequisite the multi-app
   vision adds. Should land before the desktop companion's live-session features are
   attempted, not as part of the companion app's own codebase.
4. **DM desktop companion, v1** (§6) — recommend starting narrow: session transcription +
   soundboard + `dnd-oracle` as a bundled MCP tool, no narration/co-DM agent yet, no
   second-screen yet. Prove the "thick client on the DM's own Linux box, talking to the
   website's API" shape end-to-end on the smallest useful slice before adding the more
   speculative pieces (co-DM narration agent, adaptive "read the room" music from
   `docs/obsidian-plugin-inspiration.md`'s future-idea section, second-screen projection).
5. **Player app** (§7) — as a mode within the same client, once there's an actual desktop
   client to add a mode to.
6. **P5/P6/P7** (calendars/timelines, play mode, hardening) — unchanged, still after the
   above in the existing roadmap; not re-evaluated by this research pass.

## 9. Explicitly deferred / not doing

- **No bespoke rules/SRD database.** `dnd-oracle` solves this; don't rebuild it.
- **No file-based (markdown/JSON) state anywhere in the companion app.** Every reference
  repo that tried this (open-tabletop-gm, project-d20) is explicitly a poor fit —
  DNDWORLDAPP's database via its own API is the one source of truth, full stop. The
  companion holds a live LLM session and UI state, nothing durable.
- **No separate player-app binary yet** (§7) — a mode toggle first.
- **No graph rendering of tag membership as edges** (§3) — node color/filter only.
- **No Docker-only/cloud-first self-host story** (§5) — root `docker-compose.yml` stays
  authoritative.
