# Audit — 2026-08-24

**Status: 1.1–1.5 and 2.1–2.4 fixed the same day, each with a regression assertion added
to `smoke.mjs` per §6.5. 3.1 (`@fastify/static` advisories) deliberately deferred — see
its section for why. Details on what shipped and what did not are inline below.**

The best-practices / bugs pass that HANDOFF.md §3 has been carrying as "still owed".
Run against `b9a43c5` (P4.3), on a clean checkout, with a real server on an empty data
dir. Every finding below was **reproduced against a running server**, not inferred from
reading — the probe transcript is quoted inline.

Baseline first, because it matters for reading the rest: **the four leak surfaces the
smoke suite already asserts all hold.** A player cannot see a `dm` page in the tree,
cannot fetch it by id (404, not 403), cannot find its text in search, and cannot find
text from inside a `:::secret` block in search. The security model works exactly where it
was tested.

Every finding below is on a surface added *after* those four tests were written. This is
§6.5 ("a leak surface needs a test in the same commit that opens it") going unenforced
three times in a row — P2's unresolved-links, P4.1's map reads, P4.2's tiles.

`npm test` (31) and `npm run typecheck` are green at HEAD.

## Severity 1 — DM content readable by a player

### 1.1 `unresolved-links` has no visibility filter at all — **fixed**

`unresolvedLinks()` now takes the viewer and joins `links → nodes`, filtered through the
same `readableSql()` `backlinksFor()` already used. Regression: `smoke.mjs`, "leak-surface
regressions" section, "F1a".

`services/nodes.ts::unresolvedLinks(worldId)` takes a world id and no viewer. The route
(`routes/worlds.ts`) calls `viewerForWorld()` for membership and then passes nothing
about that viewer down. Any member — including a `guest` — gets the raw `target_text` of
every unresolved wiki link in the world.

```
LEAK   F1a/unresolved-links: link text from a dm-only page
        player got: ["Grand Vizier Zathrax","The Ossuary Of Nine Mouths"]
```

`Grand Vizier Zathrax` was written only in the body of a `visibility: "dm"` page. Search
correctly returns nothing for it; this endpoint hands it over.

### 1.2 The same endpoint leaks links written inside `:::secret` blocks — **fixed**

`reindexLinks` now parses `stripSecrets(row.body_md)`, so a wikilink inside a `:::secret`
block never becomes a `links` row at all — for anyone, including the DM, matching the
precedent §7.2 already sets for search (excluded entirely rather than given a second,
role-gated index). A one-time boot backfill (`backfillLinksStrippedOfSecrets`, gated
through the same `_migrations` ledger the SQL migrations use, run once from `index.ts`)
re-derives every node's `links` rows on first boot after this fix, so rows built from
secret content before the fix don't linger. Regression: `smoke.mjs` "F1b" plus a "DM
still sees the dm-page link, but not the secret one" pair, since the DM losing the
secret-block link too was the one surprising part of this fix.

`The Ossuary Of Nine Mouths` above was written inside a `:::secret` block on a **public**
page. It leaks for a different reason than 1.1, and the root cause is a one-line
asymmetry in `services/nodes.ts`:

```
line 259  reindexLinks:  for (const link of parseWikilinks(row.body_md))      // raw
line 283  reindexFts:    insertFtsRow.run(..., stripSecrets(row.body_md))     // stripped
```

When secret blocks landed (migration `0003`), the FTS indexer was deliberately moved into
JS so it could call `stripSecrets()`. The **link** indexer sitting eight lines above it
was not given the same treatment. So a wikilink inside a secret block becomes a real
`links` row, and then surfaces through both this endpoint and `backlinksFor()` — a
`[[Target|Label]]` in a DM aside on a public page shows up in the target's backlinks
panel, label and all.

**Fix:** pass the viewer into `unresolvedLinks()` and join `links → nodes` with
`readableSql()`, the same as `backlinksFor()` already does; and index
`stripSecrets(row.body_md)` in `reindexLinks` so secret-block links never become rows.
Note the second half is a data migration, not just a code change — existing `links` rows
built from secret blocks are already in the DB.

### 1.3 Both map read routes skip the node's own visibility — **fixed**

`getMap()` and `listMarkers()` both now call `requireVisibleNode()` before returning
anything. Regression: `smoke.mjs` "F2a"/"F2b".

`routes/maps.ts` uses `viewerForNode()` for the two GETs. That helper only resolves
*which world the node is in* and *what role you have there* — it deliberately does not
check whether you can see the node (`http/context.ts`, and it is right not to; the write
paths layer `requireVisibleNode` on top via `requireMapNode`). The two read paths never
layer anything on top.

```
LEAK   F2a/GET map of a dm-only map node
        status 200 (expect 404); body {"map":{"nodeId":"vudjtyu4",
        "assetUrl":"/media/80/803fdf25...png","width":2400,"height":1600,...

LEAK   F2b/GET markers of a dm-only map node
        status 200, 1 markers (expect 404)
```

A player who knows a DM-only map node's id gets its dimensions, its marker set, and —
via `assetUrl` — the image itself. Node ids appear in URLs and get pasted around, and a
map that was once visible and later set to `dm` stays reachable forever.

**Fix:** `requireVisibleNode(nodeId, viewer)` at the top of `getMap` and `listMarkers`,
matching what `requireMapNode` already does for writes.

### 1.4 Marker inheritance leaks the title of a page you cannot see — **fixed**

Added `isNodeVisible()` (a non-throwing sibling of `requireVisibleNode()`) to
`services/nodes.ts`. `maps.ts`'s `targetNodeFor()` and `fields.ts`'s `toDto()` (for
`type: "link"` fields — the identical hole, same fix) both now resolve the target only
when it is visible to the viewer; an invisible target degrades to the marker/field's own
override, or `null`. Regression: `smoke.mjs`, both the marker and the link-field case.

This one is a design tension, not an oversight, and it is the most interesting finding.

`toMarkerDto()` resolves a marker's label and icon from its `target_node_id` with no
visibility check. The code comment defends this by pointing at `breadcrumbFor()` as
precedent — but a breadcrumb ancestor is a node you are already inside; a marker target
is *any node in the world*.

```
LEAK   F3/marker on a visible map inherits a dm-only page's title
        label="DM Only Briefing" targetNode={"id":"1likp251","title":"DM Only Briefing","icon":null}
```

That is a `members` marker on a `members` map — nothing about the marker is hidden — and
it hands a player the title **and the node id** of a `dm`-only page.

This collides directly with the P4.1 decision that **inheritance is the default**,
justified by LegendKeeper storing no name on 73 of 77 real pins (§10.5). Because
inheritance is the default, the leak is not an edge case — it is what happens every time
a DM drops a pin on a secret location and leaves the label blank.

**Fix:** resolve `targetNodeFor()` through `readableSql()` and fall back to the marker's
own `label`/`icon` when the target is not visible; if the marker has no override either,
return `null` and let the client render an anonymous pin. The same reasoning applies to
`fields.ts::toDto`'s `refNode` for `type: "link"` fields, which carries the identical
comment and the identical hole.

### 1.5 `/media/` and `/tiles/` are served with no authorization whatsoever — **`/tiles/` fixed, `/media/` kept as a deliberate capability URL**

`index.ts` now runs an `onRequest` hook on the `/tiles/` prefix that resolves the map
node id from the URL and calls `viewerForNode` + `requireVisibleNode` before
`@fastify/static` ever serves a byte — same "hidden means 404-shaped, here 401/403"
posture as every other read path. `/media/` was evaluated and deliberately left
unauthenticated: anonymous share links (§7.5) render a node body with **no session at
all**, and that body can embed `<img src="/media/...">`; gating it would break every
image on every shared page, and assets have no single owning node to check visibility
against regardless (one image can be reused across many bodies). Full reasoning now
lives in HANDOFF.md §8.2. Regression: `smoke.mjs`'s tile-fetch checks now assert an
authenticated fetch succeeds, an anonymous one is rejected, AND a player who loses
visibility to a map loses its tiles too.

Both `fastifyStatic` registrations in `index.ts` sit outside the API and outside the
scope hook (which returns early for anything not under `/api/v1/`). No session, no token,
no membership check.

```
LEAK   F4a/dm-only map's source image, NO auth at all
        GET /media/80/803fdf25...png -> 200 image/png
LEAK   F4b/dm-only map's TILES, NO auth at all
        tilingStatus=ready; GET /tiles/vudjtyu4/0/0/0.webp -> 200 image/webp
```

These fetches carried **no cookie and no bearer token** — they are anonymous.

The two cases differ in how exposed they actually are:

- `/media/` is content-addressed by sha256. Unguessable in practice, and "capability
  URL" is a defensible design for images — but it should be a *written* decision, not an
  accident, because it means image visibility can never be revoked.
- `/tiles/` is keyed by **map node id** — an 8-character id that is in the URL bar, in
  every tree response, and in every share-link payload. That is not a capability URL. Any
  player who has ever seen a map node's id keeps its tiles after it goes DM-only.

**Fix:** at minimum, move `/tiles/` behind a route that resolves the map node and calls
`requireVisibleNode` before streaming (an `onRequest` hook on the static prefix is
enough). For `/media/`, either do the same via `assets.world_id`, or write the capability
-URL trade-off into HANDOFF §8.2 as an explicit decision.

## Severity 2 — correctness and consistency

### 2.1 An ACL edit grant does not cover a page's sections — **fixed**

`createPost` now gates on `canEditNode(node, viewer)` instead of bare `canEdit`, matching
`nodes.ts`/`fields.ts`/`maps.ts`. `updatePost`/`deletePost` were left exactly as they
were — gating on the *post's own* creator is a deliberate, different rule (a player who
adds their own section keeps editing it) and was not what this finding was about.
Regression: `smoke.mjs`, "2.1".

`posts.ts` calls bare `canEdit(viewer.role, node.created_by, viewer.userId)` where
`nodes.ts`, `fields.ts` and `maps.ts` all call `canEditNode()` (which adds the ACL
lookup). So one grant produces three different answers on the same page:

```
ok     ACL edit grant lets the player edit the NODE body      status 200
ok     ACL edit grant lets the player add a FIELD             status 201
ISSUE  ACL edit grant lets the player add a SECTION           status 403
        {"error":{"code":"forbidden","message":"You cannot add sections to this page."}}
```

PLAN §8 P2.3 promises ACL grants cover "edit, not just read". They do, except for the
one feature the whole visibility model was built around. **Fix:** `createPost` should use
`canEditNode(node, viewer)`. (`updatePost`/`deletePost` gating on the *post's* own creator
is correct and should stay.)

### 2.2 `listMarkers` filters in JS instead of SQL — **fixed**

Folded into the 1.3 fix: `listMarkers` now builds a `visibility IN (...)` SQL fragment
(`markerVisibleSql`, mirroring `fields.ts`'s `fieldVisibleSql`) instead of fetching every
marker and filtering in JS.

```ts
const rows = (selectMarkersForMap.all(mapNodeId) as MapMarkerRow[])
  .filter((r) => (levels as string[]).includes(r.visibility));
```

Rule §6.1 is explicit: visibility composes *into the SQL*, so hidden rows are never
selected. This is the only read path in the codebase that fetches then filters. It is
functionally correct today, and it is exactly the shape that rots the first time someone
adds pagination or a count to it. `fields.ts::fieldVisibleSql` shows the right pattern
for the same 3-value case.

### 2.3 The editor drops a pending autosave on unmount — **fixed**

`Editor.tsx` now tracks the pending editor instance alongside the debounce timer and
flushes it (instead of just clearing it) on unmount and on `beforeunload`. The unmount
case (navigating within the app) is a reliable fix; the tab-close case is best-effort
only (the PATCH may not finish before the page unloads — no `keepalive`/`sendBeacon` was
added, since that's a bigger, separate change). Not covered by `smoke.mjs` (server-side
suite; this is a client timing bug) — verified by reading the effect cleanup order
(TipTap's own unmount effect runs after this one, so the editor instance is still alive
when the flush reads it) rather than a live browser session.

`Editor.tsx` debounces saves 800 ms (`AUTOSAVE_QUIET_MS`). The unmount effect clears the
timer without flushing it:

```ts
useEffect(() => () => {
  if (saveTimer.current !== null) window.clearTimeout(saveTimer.current);
}, []);
```

`NodeView.tsx:277` mounts `<Editor key={node.id}>`, so **navigating to another page
unmounts the editor**. Type a character and click a sidebar row inside 800 ms and the
edit is silently gone. There is no `beforeunload` guard either, so closing the tab in the
same window loses it too.

The window is short, but this is a no-Save-button, always-editable design — silent loss
is the one failure mode it cannot afford. **Fix:** flush on unmount rather than clear
(`onChangeRef.current(ed.getMarkdown())` if a timer is pending), and add a
`beforeunload` handler while a save is in flight.

### 2.4 Tiling has no cleanup and no crash recovery

`startTiling()` (`maps.ts`) is fire-and-forget by design, which is fine, but:

- Two `setMapImage` calls in quick succession race — the second `fs.rmSync(outDir)` runs
  while the first `sharp` job is still writing into it.
- Nothing deletes `tiles/<nodeId>/` when a map node is archived, so tile directories leak
  on disk and stay served (see 1.5).
- A restart mid-tile leaves `tiling_status = 'running'` forever, and `MapView` waits on a
  status that will never advance. A boot-time sweep resetting stale `running` rows to
  `error` would close it.

## Severity 3 — housekeeping

### 3.1 `@fastify/static` 8.3.0 has four high-severity advisories

`npm audit` reports path traversal, directory-listing disclosure, and two route-guard
bypasses (all `<=10.1.1`, fixed in 10.1.3 — a major bump from the pinned `^8.0.3`).

**I tried to exploit them in this configuration and could not:**

```
ok  traversal /tiles/..%2f..%2fworldapp.db          403
ok  traversal /tiles/%2e%2e/%2e%2e/worldapp.db      404
ok  traversal /media/..%2f..%2fworldapp.db          403
ok  traversal /tiles/..%5c..%5cworldapp.db          403
ok  directory listing /tiles/                       404
ok  directory listing /media/                       404
```

Directory listing is off, and the route-guard bypasses need a guard to bypass — these
prefixes have none (which is finding 1.5, not this one). So this is worth scheduling on
principle, not treating as an open hole. Note the ordering: **fix 1.5 first**, because
adding an auth hook to `/tiles/` is precisely what makes the "route guard bypass via
encoded path separators" advisory start to matter.

### 3.2 Smaller items

- `updateMarker()` calls `requireMapNode()` directly and then again inside
  `requireOwnMarker()` — two identical ACL subqueries per marker edit.
- `getTree()` runs a correlated `child_count` subquery per row, each with its own ACL
  `EXISTS`. Fine at current scale; the first thing to profile if a large world feels slow.
- `reindexLinks` mints link ids with `shortId(12)` while `lib/id.ts` documents 8 for nodes
  and `longId(20)` for everything else. Harmless, but it is a third convention.

## Suggested order

1. **1.3 + 1.5** — same feature area, both need `requireVisibleNode`, one commit each with
   a smoke assertion. This is the biggest exposure and the cheapest fix.
2. **1.1 + 1.2** — one endpoint plus the `reindexLinks` asymmetry. Needs a backfill for
   `links` rows already built from secret bodies.
3. **1.4** — decide the inheritance-vs-visibility rule first, then implement in
   `maps.ts` and `fields.ts` together.
4. **2.1, 2.3** — small, self-contained, user-visible.
5. **2.2, 2.4, 3.1** — cleanup, schedule freely.

Per §6.5, every one of 1.1–1.5 needs its assertion added to `smoke.mjs` in the same
commit as its fix. The probe script used for this audit maps 1:1 onto those assertions.
